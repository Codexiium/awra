Running log of deliberate shortcuts, deferred work, and things worth revisiting as the Supabase migration (see `plan.md`) continues. Grouped by area, not by phase.

## Performance

- **Every route is server-rendered per-request (ƒ), none are static.** The root layout (`app/layout.tsx`) fetches nav products through `lib/catalog.ts`, which goes through `lib/supabase/server.ts` — and that always calls `cookies()` (a request-time API), which forces the whole tree dynamic even for purely static marketing pages (`/about`, `/faq`, `/privacy-policy`, etc). Fix later: give the public, unauthenticated catalog reads (nav data, `/shop`, `/product/[slug]`, etc.) a cookie-free Supabase client so those pages can go back to being static, and keep the cookie-based client only where auth state actually matters (account pages, cart/wishlist sync).
- **`/shop` has no real pagination.** `getProducts()` returns the full filtered set with no `LIMIT`/`OFFSET` — moot at 4 products today, but needs revisiting (or at least a `limit`) before the catalog grows.
- **Search is `ILIKE` substring matching**, not Postgres full-text search (`tsvector`/`to_tsquery`). Fine at 4 products; won't scale gracefully — revisit with a `tsvector` column + GIN index if the catalog grows.

## Data model approximations

- **`product_variants` were seeded as a full size × color cross-product** with synthetic `stock_qty` (25 if the mock size was "available", 0 otherwise), because the original mock data only modeled per-size availability, not real per-combination inventory. This is not real stock data — revisit before actually relying on `stock_qty` for anything beyond checkout's happy-path decrement test.
- **Only 4 shared "dummy" product images exist** (`dummy_1..4` in the `product-images` bucket), randomly assigned as each product's `primary` image; no `secondary` or `gallery` images were seeded. Needs real per-product photography eventually — `ProductImage.tsx` and the `product_images` schema already support it without further code changes.

## Deferred functionality (tracked in `plan.md`'s phased rollout)

- ~~Cart and wishlist are local-only~~ **Done (Phase 4).** Logged-in users now sync to `cart_items`/`wishlists` via direct client-side Supabase calls (`lib/supabase/sync.ts`), RLS-scoped to `auth.uid()`. `CartWishlistSync.tsx` (mounted in the root layout) merges any local guest cart/wishlist into the server tables on login and clears local state on logout so it can't leak to the next guest on the same browser. Guests unchanged (localStorage only). One gotcha hit and fixed along the way: `wishlists` upserts must use `ignoreDuplicates: true` (`ON CONFLICT DO NOTHING`), not the default merge-duplicates — a merge-duplicates upsert issues an actual `ON CONFLICT DO UPDATE`, which needs an `UPDATE` grant that was deliberately never given to a table with nothing to update on conflict.
- ~~Promo codes are hardcoded client-side~~ **Done (Phase 4).** `applyPromoCode` is now a real Server Action (`lib/promo/actions.ts`) validating against the seeded `promo_codes` table via a service-role admin client (`lib/supabase/admin.ts`) — needed because `promo_codes` intentionally has no anon/authenticated select policy, so even the per-request cookie client can't read it. `useCartStore.applyPromoCode` is now async.
- ~~Checkout is 100% mock~~ **Done (Phase 5).** `placeOrder` (`lib/checkout/actions.ts`) re-reads the cart server-side, validates stock, recomputes totals, and creates real `orders`/`order_items`/`payments` rows, then hands off to the dummy provider (`lib/payments/`) at `/dummy_pay`, which posts to `/api/payments/dummy/confirm` (service-role client, explicit order-ownership check) to flip `payments.status`/`orders.payment_status` — modeled on how a real webhook would work, per `plan.md` §5a. `/checkout/success` now reads the real paid order (404s if it isn't actually paid). `/checkout` and `/checkout/success` are gated behind login (`proxy.ts`), and `/login` now supports a `?next=` redirect so checkout resumes after signing in.
  - **Caught two more real bugs via live end-to-end testing** (same REST-simulation approach used in Phase 4): (1) inserting into `orders` calls `nextval(order_number_seq)` for the `order_number` default, which needs its own `GRANT USAGE ON SEQUENCE` — table-level grants don't cover sequences, so every `authenticated` insert failed with `permission denied for sequence` until `supabase/migrations/20260914070000_order_number_seq_grant.sql` was added. (2) confirmed `product_variants` stock decrement is correctly blocked for regular users (no UPDATE grant, by design) and only works via the admin client inside `placeOrder` — this was intentional, verified rather than assumed.
  - **Known limitation**: `placeOrder`'s multiple writes (order → order_items → stock decrement → cart clear → payment) are not wrapped in a single database transaction/RPC, so a failure partway through can leave inconsistent state (e.g. an order created but stock not decremented). Acceptable for a dummy/demo flow; a real production checkout would want this as a Postgres function called via `.rpc()` for atomicity.
- ~~`/account/addresses` is read-only~~ **Done (Phase 6).** Real CRUD via `lib/account/actions.ts` (`createAddress`/`updateAddress`/`deleteAddress`/`setDefaultAddress`) and a client `AddressList`/`AddressForm` pair. Setting a new default unsets the old one first in a separate statement (two sequential writes, not a single transaction — matches the `addresses_one_default_per_user` partial unique index, which only allows one `is_default = true` row per user). Verified live: create-as-default correctly demotes the previous default, update/set-default/delete all work, and anon correctly can't write to `addresses` at all.
- ~~`/account/settings` "Save Changes" is a no-op~~ **Done (Phase 6).** `updateProfile` (same file) persists `full_name`/`phone` to `profiles`, and — if the submitted email differs from the session's — calls `supabase.auth.updateUser({ email })` to kick off Supabase's real re-confirmation flow, surfacing a distinct "check your inbox" message rather than pretending the change is immediate.
- ~~No admin/back-office exists~~ **Done (Phase 7).** Added an `/admin` panel gated by a new `profiles.is_admin boolean` column: paginated order management (status now `pending/accepted/processing/shipped/delivered/cancelled`, up from the original 4-value enum, plus new `tracking_carrier`/`tracking_number`/`tracking_url`/`shipped_at`/`delivered_at` columns on `orders`), full product CRUD including the first real image-upload implementation in this project (`product-images` bucket, previously untouched by any code path), variant/stock management, a paginated user list with admin promotion/demotion, and promo code CRUD. `requireAdmin()` (`lib/admin/auth.ts`) 404s rather than redirecting non-admins, to avoid confirming the route's existence to a prober. All admin writes go through the existing `createAdminClient()` service-role pattern (no new RLS policies were added) since `orders`/`products`/`product_variants`/`product_images`/`payments` have no write grant for `authenticated` by design.
  - **Real security bug caught and fixed during design, before any code shipped**: adding `profiles.is_admin` as a plain column would have been a privilege-escalation hole — `profiles_update_own`'s RLS policy only checks row ownership, not which columns change, and the existing `grant select, update on public.profiles to authenticated` (table-wide) would have let any signed-in user `PATCH /rest/v1/profiles?id=eq.<own uid> {"is_admin": true}` and self-promote, bypassing the app entirely. Fixed by replacing the table-wide grant with a column-level one (`grant update (full_name, phone) on public.profiles to authenticated`) in the same migration that adds the column. Verified live: the self-promotion PATCH now returns `403 permission denied for table profiles`, while the legitimate `full_name`/`phone` update from Settings still succeeds.
  - **Real bug caught via `bun run build`**: `app/admin/products/ProductImagesSection.tsx` (a `"use client"` component) imported `getPublicImageUrl` from `lib/catalog.ts`, which also imports `lib/supabase/server.ts` (uses `next/headers`, server-only) — pulling a server-only module into the client bundle and failing the build. Fixed by extracting `getPublicImageUrl` (a pure string function, no actual Supabase dependency) into its own `lib/storage.ts`, which `lib/catalog.ts` now re-exports for existing server-side callers. Any future client component that only needs image URL formatting should import from `lib/storage.ts` directly, not `lib/catalog.ts`.
  - New orders still default to `status = 'processing'` (unchanged) rather than `'pending'` — `placeOrder` never sets status explicitly, so this was a deliberate no-op for existing checkout behavior. `pending` exists in the enum for admin use (e.g. parking an order) but isn't where new orders start.
  - Admin-set `rating`/`review_count` on the product form are a deliberate temporary stand-in, not aggregated data — the plan was to omit them as fabricated-content, but the client's underlying schema already carries placeholder values here and the admin should be able to set them until a real review system replaces this.
- **Reviews stay fully hardcoded/dummy** on `/product/[slug]` (two fake reviewer blocks) — this was an explicit decision, not an oversight; no `reviews` table or submission flow exists or is currently planned.
- **Only a `dummy` payment provider is planned.** `lib/payments/` (provider interface + registry) and the `payments` table are designed to make adding Razorpay/Stripe/etc. later a matter of "add a provider module," but no real provider is implemented or scheduled beyond that groundwork.

## Catalog scope (client decision)

- **The "collections" concept was removed entirely** — no `collections` table, no `collection_id` FK on `products`, no `/collections` route, no collection filters/nav/footer links anywhere in the app. This was a deliberate client decision, not a partial migration: `Product.collection` no longer exists on the type, and `lib/catalog.ts` has no collection-aware functions left.
- **The catalog is trimmed to exactly 4 products**, named `001`–`004` (no descriptive names) — also a client decision. `app/data/mockProducts.ts` and `scripts/seed.ts` were updated to match, so re-seeding a fresh environment reproduces this same 4-product, no-collections state. If the catalog grows again later, decide deliberately whether numbered-only naming and the no-collections structure still apply, rather than assuming the old 12-product/collections model should come back.
- ~~Categories consolidated to 1~~ **Superseded — categories removed entirely.** After a brief stop at a single "Special" category, the client decided there should be no category concept at all, just products (same treatment as collections). Dropped `products.category_id` and the `categories` table; deleted `/category/[slug]`; removed the shop sidebar category filter, the header's category mega-menu (the "SHOP" mega-menu had nothing left to show once categories were gone, so it's a plain link now), the homepage's "Discover by Category" tile section, and `Product.category`/`ProductCategory` from the type layer. While in `app/page.tsx`, also fixed a real bug this surfaced: "Best Sellers" was `allProducts.slice(4, 8)`, which is empty once the catalog only has 4 products — it now sorts the same 4 by `reviewCount` instead. With only 4 products total, "Featured" and "Best Sellers" necessarily show the same items in different orders; there's no way to give them disjoint sets without arbitrarily hiding products.
- **Unverified brand/origin/courier claims were stripped from marketing copy**: "Designed in NYC and constructed in Europe," "Paris warehouse," "PARIS / NEW YORK," "PHOTOGRAPHED IN PARIS & NEW YORK," and every "DHL" mention (checkout delivery option, FAQ, shipping page, homepage banner) — none of these were ever true/confirmed, so they read as made-up claims rather than real brand facts. Shipping copy now says generic "express air freight" with no named courier. If a real courier partner or manufacturing location is confirmed later, reintroduce it deliberately rather than restoring the old placeholder text.

## Infra / operational gotchas worth remembering

- **Tables created via a direct `psql` connection don't get Supabase's usual default privilege grants.** Even with correct RLS policies, `anon`/`authenticated`/`service_role` had zero table-level access until an explicit `GRANT` migration (`supabase/migrations/20260913200100_grants.sql`) was added. Anyone adding new tables by hand (rather than through the Supabase dashboard/CLI-managed flow) needs to remember this or every query will fail with `permission denied` despite RLS looking correct.
- ~~No Supabase CLI is installed/linked~~ **Resolved.** The CLI is now available (`bunx supabase`, added as a dev dependency and logged in) and linked to the project (`supabase link --project-ref ...`). The three migrations previously applied by hand via raw `psql` were reconciled into the CLI's remote migration history with `supabase migration repair --status applied <versions> --linked` (without re-running their SQL) so `supabase migration list` now shows local/remote in sync. From here on, use `supabase migration new <name>` + `supabase db push` for schema changes instead of raw `psql -f`.
- **Email confirmation is required on signup** (by design, per an earlier decision) — new accounts can't log in until the confirmation link is clicked, which matters for local testing (need a real inbox, e.g. a mailinator-style address, to complete signup manually; there is no service-role bypass wired into the app for this).
- **`.env.local` holds real, sensitive secrets**: `SUPABASE_SECRET_KEY` (bypasses RLS) and two Postgres connection strings with a plaintext DB password (`SUPABASE_DB_DIRECT_URL`, `SUPABASE_DB_TRANSACTIONAL_URL`). It's gitignored, but worth a reminder never to paste its contents anywhere (issues, PRs, logs, chat) or commit it under a different filename.
- **`next.config.ts` has `images.dangerouslyAllowLocalIP: true`**, added because this dev sandbox resolves the Supabase storage hostname through NAT64 (`64:ff9b::/96`) to an address Next 16's new image-optimization SSRF guard flags as "private." `remotePatterns` already restricts image fetches to the exact Supabase hostname+path, so this is safe here, but it's a workaround for *this* network's DNS behavior (per Next's own docs, this scenario is specifically about split-horizon DNS/VPC setups) — re-check whether it's actually still needed once deployed somewhere with normal public DNS resolution (e.g. Vercel), since it may not be there.

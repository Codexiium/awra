# TODO / Known Trade-offs & Concerns

Running log of deliberate shortcuts, deferred work, and things worth revisiting as the Supabase migration (see `plan.md`) continues. Grouped by area, not by phase.

## Color removed as a product-variant dimension entirely (client decision)

- **Products now have only sizes — color is gone from the data model, not just the UI.** This follows on from the earlier storefront-only color-hiding pass (see the "Color selection removed from the storefront" entry below): the client clarified that colors will eventually become separate standalone products rather than variants of one, so the `size x color` cross-product in `product_variants` was collapsed for real. Migration `20260918142243_remove_variant_colors.sql`: merged the (up to two) color rows per size into one row per `(product_id, size)` — `available` via `bool_or` across colors, `stock_qty` via `sum` (verified live: product 2's `XS` had drifted to 24/25 stock between its two colors from earlier manual testing, correctly summed to 49) — then dropped `product_variants.color_name`/`color_hex` and retightened the unique constraint to `(product_id, size)`. `cart_items.color_name` and `order_items.color_name` were dropped too; both tables had no real data at the time (checked live before writing the migration — one stray abandoned cart row, zero orders), so this was a clean removal, not a data-loss trade-off.
- **Every touchpoint keyed on `(product_id/productId, size, color)` is now keyed on `(product_id/productId, size)` alone**: `lib/checkout/actions.ts` (variant stock lookup/decrement, `order_items` insert), `lib/supabase/sync.ts` and `CartWishlistSync.tsx` (`cart_items` upsert), `app/api/cart/route.ts`, `useCartStore`'s `addItem`/`removeItem`/`updateQuantity` (dropped the `selectedColor` parameter — `CartItem` no longer has a `selectedColor` field), and `lib/admin/products.ts`'s `createVariant` (dropped `colorName`/`colorHex` fields; the size-uniqueness conflict message changed from "size/color combination" to "size"). `lib/catalog.ts` dropped `getDistinctSizesAndColors` in favor of `getDistinctSizes` (colors no longer exist to enumerate), and `Product`/`ProductColorOption` in `app/types/index.ts` lost the `colors` field/type entirely.
- **`scripts/seed.ts` now seeds one `product_variants` row per size** (`stock_qty: 50` when available, matching the post-migration merged live values, up from the old per-color `25`) instead of the old size × color cross-product — re-seeding a fresh project reproduces today's sizes-only state.
- Verified live end-to-end against the real project (not just `tsc`/build): a `product_id + size`-only cart insert, variant stock lookup, `order_items` insert, and stock decrement all round-tripped correctly with a real user token, mirroring `placeOrder`'s exact sequence per this project's established testing convention.

## Payments: Cash on Delivery only, online disabled (client decision)

- **Online payment is disabled; Cash on Delivery (COD) is the only working payment method.** `lib/payments/providers/cod.ts` is a new provider (no gateway redirect — payment happens in person at delivery, so it inserts a `payments` row and goes straight to `/checkout/success` rather than `/dummy_pay`). `lib/payments/registry.ts` now only registers `cod`; `lib/checkout/actions.ts` calls it explicitly and rejects any other `paymentMethod` value submitted in the form (defends against a disabled radio being bypassed client-side). `CheckoutForm.tsx`'s old mock card-number/expiry/CVC fields are gone, replaced by a COD/"ONLINE PAYMENT — COMING SOON" selector (online is a disabled radio, no backend behind it — nothing to wire up later beyond re-adding a real provider module when the business is ready).
- **`payments.provider` is now constrained to `'cod'` only.** Two migrations landed back to back: `20260916060045_add_cod_payment_provider.sql` first added `'cod'` alongside the existing `'dummy'/'razorpay'/'stripe'` for forward-compatibility, then `20260916060318_restrict_payments_to_cod_only.sql` tightened it to `'cod'` only per explicit instruction — deliberately keeping the DB matching what's actually reachable rather than provisioning for providers with no code behind them. That second migration also deleted the two orders that had `payments.provider = 'dummy'` (cascading their `order_items`/`payments`), since they were pre-launch test data, not real orders.
- **`/checkout/success`'s gate changed** from `order.payment_status === "paid"` (which a COD order never reaches — `payment_status` stays `"pending"` until money is actually collected at delivery) to "does this order have a `payments` row at all," which still rejects a guessed/bookmarked order number for an order that never actually completed `placeOrder`. The page's "PAYMENT STATUS: PAID" line now reads "PAYMENT METHOD: CASH ON DELIVERY".
- **`lib/payments/providers/dummy.ts`, `/dummy_pay`, and `/api/payments/dummy/confirm` were intentionally left in place but are now unreachable** from the live checkout flow (not registered in `registry.ts`, nothing links to `/dummy_pay` anymore) — kept as a reference implementation for whenever a real online gateway (or the dummy flow itself) needs to come back, rather than deleted.

## Performance

- **Every route is server-rendered per-request (ƒ), none are static.** The root layout (`app/layout.tsx`) fetches nav products through `lib/catalog.ts`, which goes through `lib/supabase/server.ts` — and that always calls `cookies()` (a request-time API), which forces the whole tree dynamic even for purely static marketing pages (`/about`, `/faq`, `/privacy-policy`, etc). Fix later: give the public, unauthenticated catalog reads (nav data, `/shop`, `/product/[slug]`, etc.) a cookie-free Supabase client so those pages can go back to being static, and keep the cookie-based client only where auth state actually matters (account pages, cart/wishlist sync).
- **`/shop` has no real pagination.** `getProducts()` returns the full filtered set with no `LIMIT`/`OFFSET` — moot at 4 products today, but needs revisiting (or at least a `limit`) before the catalog grows.
- **Search is `ILIKE` substring matching**, not Postgres full-text search (`tsvector`/`to_tsquery`). Fine at 4 products; won't scale gracefully — revisit with a `tsvector` column + GIN index if the catalog grows.

This is not real stock data — revisit before actually relying on `stock_qty` for anything beyond checkout's happy-path decrement test.

## Infra / operational gotchas worth remembering

- **Tables created via a direct `psql` connection don't get Supabase's usual default privilege grants.** Even with correct RLS policies, `anon`/`authenticated`/`service_role` had zero table-level access until an explicit `GRANT` migration (`supabase/migrations/20260913200100_grants.sql`) was added. Anyone adding new tables by hand (rather than through the Supabase dashboard/CLI-managed flow) needs to remember this or every query will fail with `permission denied` despite RLS looking correct.
- ~~No Supabase CLI is installed/linked~~ **Resolved.** The CLI is now available (`bunx supabase`, added as a dev dependency and logged in) and linked to the project (`supabase link --project-ref ...`). The three migrations previously applied by hand via raw `psql` were reconciled into the CLI's remote migration history with `supabase migration repair --status applied <versions> --linked` (without re-running their SQL) so `supabase migration list` now shows local/remote in sync. From here on, use `supabase migration new <name>` + `supabase db push` for schema changes instead of raw `psql -f`.
- **Email confirmation is required on signup** (by design, per an earlier decision) — new accounts can't log in until the confirmation link is clicked, which matters for local testing (need a real inbox, e.g. a mailinator-style address, to complete signup manually; there is no service-role bypass wired into the app for this).
- **`.env.local` holds real, sensitive secrets**: `SUPABASE_SECRET_KEY` (bypasses RLS) and two Postgres connection strings with a plaintext DB password (`SUPABASE_DB_DIRECT_URL`, `SUPABASE_DB_TRANSACTIONAL_URL`). It's gitignored, but worth a reminder never to paste its contents anywhere (issues, PRs, logs, chat) or commit it under a different filename.
- **`next.config.ts` has `images.dangerouslyAllowLocalIP: true`**, added because this dev sandbox resolves the Supabase storage hostname through NAT64 (`64:ff9b::/96`) to an address Next 16's new image-optimization SSRF guard flags as "private." `remotePatterns` already restricts image fetches to the exact Supabase hostname+path, so this is safe here, but it's a workaround for *this* network's DNS behavior (per Next's own docs, this scenario is specifically about split-horizon DNS/VPC setups) — re-check whether it's actually still needed once deployed somewhere with normal public DNS resolution (e.g. Vercel), since it may not be there.
  - ~~Removed~~ **Reverted.** Taken out of `next.config.ts` as part of the pre-launch hardening pass below on the theory it was purely a dev-sandbox workaround — but re-testing immediately surfaced every product image failing with "hostname resolved to private IP" against `64:ff9b::`-prefixed addresses, confirming this environment still needs it. Re-added with the flag scoped only to this NAT64 behavior. Still worth re-checking whether it's needed on whatever the actual deployment target ends up being (e.g. Vercel), since normal public DNS resolution there may not exhibit this at all.

## Pre-launch hardening pass (`analysis.md`'s "MUST BE DONE" tier)

A full security/correctness/legal/a11y/SEO sweep (`analysis.md`, generated by reading the app, schema, and grants against "what stops this from being a real store taking real money from real customers") was done and its MUST BE DONE tier implemented on the `prelaunch/must-be-done` branch. Most items were built outright (atomic `place_order()` closing the stock-race/non-transactional-checkout/order-forgery findings together, the dummy payment surface deleted, per-page admin authorization, the open-redirect fix, password reset, promo code hardening, security headers, env validation, restock-on-cancel, a pluggable email module, error boundaries, an accessibility sweep, and per-page SEO metadata). A few items were explicitly scoped out of that pass and are tracked here instead:

- **Rate limiting (`analysis.md` SEC-6) is not implemented.** Nothing throttles sign-in, sign-up, promo code validation, `placeOrder`, or the contact form — Supabase applies its own limits to `auth.*` calls, but none of this app's own Server Actions/Route Handlers are protected. The plan when this gets picked up: **Upstash Redis** with `@upstash/ratelimit` (the de-facto Next.js-standard approach — serverless-friendly, works correctly across multiple instances/edge, generous free tier), keyed **per-IP** for anonymous paths (sign-in, sign-up, contact form) and **per-user-id** for authenticated ones (promo validation, `placeOrder`). Needs an Upstash account provisioned and `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` added to the environment before implementation — that provisioning step is why this was deferred rather than built speculatively.
- **Real transactional email provider.** The pluggable `lib/email/` module (mirroring the existing `lib/payments/` provider-registry shape) ships wired to **Supabase SMTP** for now. Swapping to **Resend** (modern API, first-class Next.js/React-Email support, generous free tier) later is meant to be a matter of adding `lib/email/providers/resend.ts` and changing the registry's active key — no call-site changes anywhere order confirmation/shipping-notification/contact-form emails are sent from. Needs a Resend account + API key + verified sending domain when that swap happens.
- **Error monitoring/APM.** Every previously-silent `catch`/error-return site across `lib/checkout/`, `lib/admin/`, and `lib/promo/` now at least does `console.error(error)` before returning its friendly user-facing message, so failures are visible in server logs — but nothing aggregates, alerts on, or tracks them over time. Wiring **Sentry** (or an equivalent) is still needed, plus uptime checks on `/` and `/api/cart`, once a vendor/account is chosen.
- **Tests and CI (`analysis.md` OPS-4).** Still zero automated tests and no CI pipeline (~8,500+ lines including checkout, stock, pricing, payments, and admin authorization). When this gets built: Vitest for the extracted pure functions (`lib/checkout/validateAddress.ts`, `lib/pricing/shipping.ts`), an RLS/grant assertion suite using the project's established live-REST-simulation testing method (see `AGENTS.md`), a two-concurrent-`place_order()`-calls oversell test (now meaningful since `place_order()` is atomic — this is exactly the test that would prove BUG-1 stays fixed), and a GitHub Actions workflow running `bunx tsc --noEmit` + `bun run lint` + `bun run build` + the test suite on push. The RLS/live tests would need `SUPABASE_SECRET_KEY` provisioned as a CI secret.
- **Real business facts** (`analysis.md` LEGAL-1/LEGAL-3/LEGAL-4) were explicitly left untouched this pass: the fabricated "742 Gothic Arch Ave, New York" contact address, "ARWA ARCHIVE INC." as the privacy policy's named entity, and the three-sentence placeholder privacy/terms/returns/shipping pages, plus GST being charged with no GSTIN displayed and no tax invoice generated. None of these can be fixed with fabricated content — they need the actual registered business name, address, GSTIN (or confirmation GST isn't actually registered), and real return/shipping commitments before they can be written honestly.
